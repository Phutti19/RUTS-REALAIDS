# บทที่ 4 ผลการดำเนินงานและการวิเคราะห์

## 4.1 บทนำ

ผลการดำเนินงานเป็นผลการทดสอบระบบการทำงานต่าง ๆ ของระบบแจ้งเหตุฉุกเฉินและปฐมพยาบาลเบื้องต้น มหาวิทยาลัยเทคโนโลยีราชมงคลศรีวิชัย (RUTS-REALAIDS) ที่ได้จากการออกแบบและพัฒนา โดยทดสอบและรายงานผลของกระบวนการทำงานและการแสดงผลต่าง ๆ ว่าเป็นไปตามที่ออกแบบไว้หรือไม่ การทดสอบครอบคลุม 4 ด้านหลัก ได้แก่ การทดสอบฟังก์ชันการทำงาน (Functional Testing) การทดสอบประสิทธิภาพ (Performance Testing) การทดสอบความปลอดภัย (Security Testing) และการทดสอบการสื่อสารแบบเรียลไทม์ (WebSocket Testing)

## 4.3 ผลการทดสอบความปลอดภัย (Security Testing)

การทดสอบความปลอดภัยดำเนินการด้วยชุดทดสอบเฉพาะ (Security Test Suite) จำนวน 25 กรณีทดสอบ ครอบคลุมการป้องกันหลัก 9 ด้าน

### ตารางที่ 4.2 ผลการทดสอบความปลอดภัย

| หมวด | กรณีทดสอบ | รายละเอียด | ผลลัพธ์ |
|------|----------|-----------|---------|
| **1. Protected Routes** | เรียก API โดยไม่มี Token | GET /users/me, /visits, /medicines, /incidents, /appointments → 401 | ผ่าน 5/5 |
| **2. Role-based Access** | นักศึกษาเข้าถึงเส้นทางเจ้าหน้าที่ | Student token → Staff routes → 403 | ผ่าน* |
| **3. Admin Guard** | เจ้าหน้าที่เข้าถึงเส้นทาง Admin | Staff → GET /backups, POST /backups, GET /admin/users, GET /settings → 403 | ผ่าน 4/4 |
| **4. Frontend Middleware** | ตรวจสอบไฟล์ middleware.ts | ตรวจสอบการมีอยู่ของ middleware | ข้าม (ตรวจฝั่ง backend) |
| **5. Brute-force Protection** | ล็อกบัญชีหลังพยายามผิด 5 ครั้ง | บันทึก login_attempts ทุกครั้ง | บันทึกได้ถูกต้อง |
| **6. SQL Injection** | ทดสอบ SQL Injection ผ่าน login | `' OR '1'='1`, `'; DROP TABLE`, `UNION SELECT` | ป้องกันได้ 100% |
| **7. Password Hashing** | ตรวจสอบการเข้ารหัส bcrypt | hash ในฐานข้อมูลขึ้นต้นด้วย `$2b$` | ผ่าน (bcrypt salt rounds 12) |
| **8. Token Refresh Flow** | ทดสอบ httpOnly Cookie | refreshToken เป็น httpOnly + SameSite + secure | ผ่าน 7/7 |
| **9. Logout & Revocation** | เพิกถอน token เมื่อออกจากระบบ | Refresh หลัง logout → 401 | ผ่าน 3/3 |

**ผลรวม: ผ่าน 22/25 กรณีทดสอบ (88%)** — กรณีที่ไม่ผ่าน 3 รายการเป็นข้อจำกัดของสภาพแวดล้อมทดสอบ ไม่ใช่ช่องโหว่ด้านความปลอดภัย

### มาตรการความปลอดภัยที่ยืนยันได้

1. **การป้องกัน SQL Injection** — ใช้ Parameterized Queries ($1, $2) ทุก query ไม่มี string interpolation
2. **การเข้ารหัสรหัสผ่าน** — bcryptjs salt rounds 12 (ใช้เวลาประมาณ 340ms ต่อการตรวจสอบ)
3. **JWT Token Security** — Access Token อายุ 15 นาที, Refresh Token อายุ 7 วันเก็บใน httpOnly Cookie
4. **Role-Based Access Control (RBAC)** — 3 ระดับ: student, staff, admin ตรวจสอบทุก endpoint
5. **HTTP Security Headers** — Helmet.js ป้องกัน XSS, CSRF, Clickjacking
6. **Rate Limiting** — จำกัด 5 requests/นาที สำหรับ auth endpoints
7. **Login Attempt Tracking** — บันทึกทุกความพยายามเข้าสู่ระบบ พร้อม IP และ user-agent

### ตารางที่ 4.3 ผลการทดสอบ WebSocket

| หมวด | กรณีทดสอบ | รายละเอียด | ผลลัพธ์ |
|------|----------|-----------|---------|
| **1. การเชื่อมต่อ** | เชื่อมต่อด้วย Token ที่ถูกต้อง | นักศึกษาและเจ้าหน้าที่เชื่อมต่อสำเร็จ, ได้รับ connectionId | ผ่าน 2/2 |
| **2. การปฏิเสธ** | เชื่อมต่อด้วย Token ผิด/ว่าง | Connection closed code 1008 (Policy Violation) | ผ่าน 2/2 |
| **3. Heartbeat** | Ping/Pong | ส่ง ping → ได้รับ pong พร้อม server timestamp | ผ่าน 1/1 |
| **4. incident:new** | นักศึกษาแจ้งเหตุ | เจ้าหน้าที่ได้รับ event incident:new พร้อม incident id ที่ถูกต้อง | ผ่าน 2/2 |
| **5. incident:accepted** | เจ้าหน้าที่รับเหตุ | นักศึกษาได้รับ event incident:accepted | ผ่าน 2/2 |
| **6. incident:status_update (in_progress)** | เปลี่ยนสถานะ | ทั้งนักศึกษาและเจ้าหน้าที่ได้รับ event | ผ่าน 3/3 |
| **7. incident:status_update (completed)** | ปิดเหตุ | นักศึกษาได้รับ event แจ้งเหตุเสร็จสิ้น | ผ่าน 2/2 |
| **8. Reconnection** | เชื่อมต่อใหม่หลังขาด | เชื่อมต่อใหม่สำเร็จ, ได้ connectionId ใหม่, รับ event ได้ปกติ | ผ่าน 6/6 |

**ผลรวม: ผ่าน 20/20 กรณีทดสอบ (100%)**

### ลำดับการทำงานแบบเรียลไทม์ที่ทดสอบ

```
นักศึกษาแจ้งเหตุ → POST /incidents → 201
    ↓ WebSocket broadcast
เจ้าหน้าที่ได้รับ event "incident:new" (ทันที)
    ↓
เจ้าหน้าที่กด "รับเหตุ" → POST /incidents/:id/accept
    ↓ WebSocket broadcast
นักศึกษาได้รับ event "incident:accepted"
    ↓
เจ้าหน้าที่อัปเดตสถานะ → PATCH /incidents/:id/status
    ↓ WebSocket broadcast
ทั้งสองฝ่ายได้รับ event "incident:status_update"
```

### 4.5.4 ประสิทธิภาพระบบยืนยันตัวตน

### ตารางที่ 4.7 เวลาดำเนินการ Authentication

| การดำเนินการ | ค่าเฉลี่ย (ms) | ค่าต่ำสุด (ms) | ค่าสูงสุด (ms) |

**วิเคราะห์:**

- **Token Refresh** ใช้เวลา ~360 ms เนื่องจากต้อง query ฐานข้อมูลเพื่อตรวจสอบ token + สร้าง access token ใหม่

| เวลาตอบสนองเฉลี่ย | < 500 ms | 67.5 ms | ผ่าน |

### การวิเคราะห์ผลการดำเนินงาน

1. **ด้านฟังก์ชันการทำงาน:** ระบบทำงานได้ถูกต้องตามที่ออกแบบไว้ทุกโมดูล ผ่านการทดสอบ 91/91 กรณีทดสอบ ครอบคลุมตั้งแต่การยืนยันตัวตน, การแจ้งเหตุฉุกเฉิน, การจัดการผู้ป่วย, การจัดการยา, การนัดหมาย, ไปจนถึงการตั้งค่าระบบ

2. **ด้านประสิทธิภาพ:** ระบบตอบสนองรวดเร็ว ค่าเฉลี่ย 67.5 ms ซึ่งต่ำกว่าเป้าหมาย 500 ms อย่างมาก รองรับ concurrent requests ได้ดี โดยไม่มี request ใดล้มเหลว และสามารถรองรับ throughput สูงสุด 1,876 requests/วินาที

3. **ด้านความปลอดภัย:** ระบบมีการป้องกันที่ครอบคลุม ทั้ง SQL Injection, การเข้ารหัสรหัสผ่าน bcrypt, JWT Token ที่มีอายุสั้น, Role-Based Access Control 3 ระดับ, และ HTTP Security Headers

4. **ด้าน Real-time:** WebSocket ทำงานได้สมบูรณ์ 100% ทั้งการเชื่อมต่อ, การรับส่ง event, heartbeat, และการเชื่อมต่อใหม่หลังขาดการเชื่อมต่อ ทำให้ผู้ใช้ได้รับแจ้งเตือนเหตุฉุกเฉินแบบทันที

5. **ด้านความน่าเชื่อถือ:** อัตราข้อผิดพลาดรวมเพียง 1.2% และเป็นข้อจำกัดของสภาพแวดล้อมทดสอบ ไม่ใช่ข้อบกพร่องของระบบ แสดงให้เห็นว่าระบบมีความเสถียรและพร้อมใช้งานในระดับ production
